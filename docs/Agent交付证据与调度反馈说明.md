# Agent 交付证据与调度反馈说明

## 1. 为什么需要正式交付凭证

过去工作项进入 `Completed` 只表示 Agent 已经把结果提交给人，并不等于任务已被人工认可。如果调度器直接把这种状态当成成功，就会出现两个问题：

- Agent 只要能输出文字就不断积累“成功记录”；
- 人工驳回和返工没有形成结构化反馈，后续仍可能优先派给同一个 Agent。

当前版本把三个概念分开：

1. **执行完成**：模型结束本轮工作，工作项成功提交；
2. **正式交付**：系统生成包含结论、证据、工具影响、风险和哈希的交付凭证；
3. **验收完成**：有权限的审核人明确通过或驳回交付。

只有第三项是强成功信号。

## 2. 交付凭证包含什么

每个完成的 `AgentWorkItem` 只能生成一个 `AgentDeliveryReceipt`。凭证包含：

- Agent、版本、项目、任务、Session 和工作项标识；
- Agent 的最终文字结论；
- 系统从任务、项目、Session 和 `context.read` 审计生成的证据；
- 所有业务工具调用的名称、状态、风险级别、审核模式和脱敏影响摘要；
- 自动校验结果和风险提示；
- 对交付内容计算的 SHA-256 完整性哈希；
- 待验收、通过、驳回或被新版替代的状态；
- 审核人、时间和审核意见。

证据不采信模型自述。系统不会把工具参数和完整原始返回复制进凭证，只保留 `taskId`、`documentId`、`message` 等白名单字段；密码、Key、正文和未知返回字段仍只存在于原始受控审计链路中。

## 3. 证据质量

- **基础证据**：能够证明任务、项目、Session 和版本，但没有明确上下文读取或成功工具影响；
- **强证据**：存在授权上下文读取记录，或至少一项真实业务工具已经执行。

证据质量用于提醒审核人，不代替人工验收。即使是强证据，也可能因为结论质量、业务结果或风险处理不合格而被驳回。

## 4. 调度反馈如何形成

`AgentPerformanceSignal` 使用唯一事件键防止重复记分。当前信号为：

| 事件 | 分值 | 含义 |
| --- | ---: | --- |
| 提交交付 | +2 | 弱信号，只说明已提交等待验收 |
| 最终执行失败 | -5 | 重试耗尽或陈旧任务恢复失败 |
| 人工验收通过 | +8 | 强正反馈 |
| 人工验收驳回 | -10 | 强负反馈 |
| 人工采用调度推荐 | +3 | 推荐与人工判断一致 |
| 人工改选推荐 Agent | -4 | 原推荐不符合人工判断 |
| 人工选择替代 Agent | +5 | 替代 Agent 获得选择反馈 |

调度器只使用近 180 天信号，并按时间衰减；当前项目的反馈权重高于跨项目反馈。存在人工验收样本时，页面显示的历史成功率使用人工通过率，不再用机械工作项完成率冒充业务成功率。

## 5. 页面入口与权限

- 任务详情会展示最近一份正式交付及验收状态；
- `/Agents/WorkItems/Details/{id}` 展示完整凭证和表现反馈轨迹；
- `/Agents/WorkItems` 的完成工作项提供“交付凭证”入口；
- 完整凭证仅允许系统管理员、项目负责人和项目成员访问；
- Agent 工作项管理操作仍只允许系统管理员。

## 6. 验收步骤

1. 创建一个数字员工任务，等待 Agent 提交结果；
2. 确认任务进入“待人工确认”，任务详情出现正式交付；
3. 检查结论、系统证据、工具影响、风险提示和 64 位 SHA-256；
4. 确认凭证中没有提示词、工具原始参数、Key 或未脱敏正文；
5. 点击通过，确认任务完成、凭证变为“验收通过”，记录 `HumanAccepted`；
6. 新建另一个任务并驳回，确认凭证变为“验收驳回”、自动生成返工工作项，记录 `HumanRejected`；
7. 返工再次交付时，确认旧的待验收交付被标记为“已被新交付替代”；
8. 制造低置信度派单并改选 Agent，确认推荐方和选中方分别形成反馈；
9. 再次调度同类任务，确认候选理由显示近 180 天人工验收和加权反馈。

自动化回归位于 `ToDo.Test/AgentOutcomeServiceTests.cs` 和 `ToDo.Test/AgentDispatchServiceTests.cs`。
