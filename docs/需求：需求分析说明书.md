# 需求：ToDo项目管理系统需求分析说明书

## 1. 引言

### 1.1 目的

本文档旨在**分析**和**记录**团队对 ToDo 项目管理系统的需求理解，为后续系统设计提供依据。通过本文档，团队将明确：
- 当前的业务痛点和改进方向
- 用户群体的真实需求
- 系统的功能边界和约束条件
- 需求实现的优先级和风险

本文档是**需求分析阶段**的输出物，侧重于"理解问题"而非"解决问题"。

### 1.2 范围

本文档涵盖：
- 业务背景与现有问题分析
- 用户角色与使用场景分析
- 功能需求的初步调研结果
- 非功能需求的初步分析
- 约束条件和假设
- 风险与不确定性问题

本文档**不包含**：
- 具体的技术实现方案
- 详细的界面设计
- 精确的数据库字段定义
- 完整的测试用例

### 1.3 术语与缩略语

- **EF Core**: Entity Framework Core，.NET 平台下的对象关系映射框架。
- **Razor Pages**: ASP.NET Core 的页面驱动 Web UI 开发模型。
- **AI服务**: 集成人工智能能力，提供任务智能拆分、会议纪要处理、日报自动生成等功能。

## 2. 业务背景分析

### 2.1 组织现状

本项目源于软件开发培训计划，目标是为团队协作和项目管理提供一个**统一的信息化管理平台**。

当前团队在项目管理方面存在以下特点：
- 团队规模适中，成员间协作频繁
- 项目数量较多，需要同时跟踪多个项目的进度
- 任务分配和状态变更频繁，需要清晰的追踪机制
- 存在大量会议和日报文档，缺乏统一管理

### 2.2 现有问题

通过调研分析，团队在项目管理中面临以下主要问题：

| 问题编号 | 问题描述 | 影响分析 | 优先级 |
|---------|---------|---------|-------|
| P01 | **用户权限管理混乱** | 缺乏清晰的角色定义和权限控制，可能导致数据安全风险和操作越权 | 高 |
| P02 | **项目进度难以跟踪** | 无法实时了解项目整体进展，任务分配不明确，导致责任不清 | 高 |
| P03 | **团队协作效率低下** | 信息传递不及时，任务状态不透明，沟通成本高 | 高 |
| P04 | **缺乏有效的日志记录** | 系统操作历史缺失，难以追溯关键操作的执行者和具体内容 | 中 |
| P05 | **数据统计能力不足** | 无法直观获取项目和任务的关键数据，缺乏决策支持 | 中 |
| P06 | **会议日报管理不规范** | 会议纪要和日常报告缺乏统一平台，信息分散，难以追溯和共享 | 中 |

### 2.3 改进目标

针对上述问题，系统应实现以下**高层目标**：

1. **安全性提升**：建立完善的用户认证、授权和角色管理机制
2. **透明度增强**：实现项目、任务状态的实时跟踪和可视化展示
3. **效率优化**：通过清晰的任务分配、实时状态更新和便捷的信息共享减少沟通成本
4. **可追溯性保障**：建立全面的日志记录机制，支持审计和问题追溯
5. **决策支持**：提供数据汇总和统计功能，直观展示关键指标
6. **知识沉淀**：规范会议纪要和日报管理，促进信息共享和知识积累
7. **智能化升级**：引入AI能力，进一步提升工作效率

## 3. 用户与角色分析

### 3.1 用户群体识别

通过调研，系统的预期用户群体包括：

| 用户类型 | 描述 | 用户数量（预估） |
|---------|------|----------------|
| 系统管理员 | 负责整个系统的管理和维护 | 1-2人 |
| 项目管理者 | 负责项目的创建、成员管理和进度跟踪 | 3-5人 |
| 开发人员 | 执行具体任务，参与项目协作 | 10-20人 |

### 3.2 角色层级分析

系统采用**两级角色体系**：

**系统级角色**（全局生效）：
- **systemAdmin（系统管理员）**：拥有最高权限，负责系统层面的用户管理、配置维护
- **teamMember（团队成员）**：执行具体任务，主要关注个人工作

**项目级角色**（项目内生效）：
- **ProjectRole.Admin（项目管理员）**：管理特定项目的各项事务
- **ProjectRole.Member（项目成员）**：参与项目任务执行的基础角色

### 3.3 用户故事初步采集

通过与潜在用户的沟通，初步采集以下用户故事：

| ID | 用户故事 | 角色 | 优先级 |
|----|---------|------|-------|
| US01 | 作为系统管理员，我希望能创建用户并分配角色，以便控制用户对系统的访问 | systemAdmin | 高 |
| US02 | 作为项目管理者，我希望能创建项目并管理项目成员，以便组织团队协作 | systemAdmin | 高 |
| US03 | 作为项目管理者，我希望能给任务指派负责人，以便明确责任分工 | ProjectRole.Admin | 高 |
| US04 | 作为开发人员，我希望能创建和编辑任务，以便记录和跟踪工作进展 | teamMember | 高 |
| US05 | 作为开发人员，我希望能认领未被指派的任务，以便主动承担工作 | teamMember | 高 |
| US06 | 作为项目管理者，我希望能查看项目统计信息，以便了解项目整体进度 | ProjectRole.Admin | 中 |
| US07 | 作为开发人员，我希望能提交日报，以便汇报工作进展 | teamMember | 中 |
| US08 | 作为团队成员，我希望能记录会议纪要，以便共享会议信息 | teamMember | 中 |
| US09 | 作为系统管理员，我希望能查看操作日志，以便进行审计追踪 | systemAdmin | 中 |
| US10 | 作为项目管理者，我希望能一键生成项目工作汇总，以便快速了解项目状态 | ProjectRole.Admin | 低 |

## 4. 功能需求初步分析

### 4.1 需求模块划分

基于用户故事分析，系统功能可划分为以下模块：

```
┌─────────────────────────────────────────────────────────────┐
│                      ToDo项目管理系统                         │
├─────────────────────────────────────────────────────────────┤
│  1. 用户与权限模块      - 用户管理、角色分配、权限控制           │
│  2. 项目管理模块        - 项目CRUD、成员管理、项目统计           │
│  3. 任务模块            - 任务CRUD、状态管理、认领指派           │
│  4. 分组模块            - 任务分组、分类管理                     │
│  5. 日志模块            - 操作日志记录与查询                     │
│  6. 会议纪要模块        - 会议记录与附件管理                     │
│  7. 日报模块            - 日报提交与查看                        │
│  8. AI服务模块          - 任务拆分、日报生成等AI能力             │
│  9. 数据统计模块        - 项目统计、个人工作汇总                  │
└─────────────────────────────────────────────────────────────┘
```

### 4.2 核心业务流程分析

#### 4.2.1 项目管理流程

```
创建项目 → 添加成员 → 分配任务 → 任务执行 → 状态更新 → 项目归档
   │          │          │          │          │          │
   └──────────┴──────────┴──────────┴──────────┴──────────┘
                              │
                         变更日志记录
```

#### 4.2.2 任务处理流程

```
创建任务 → (可选)指派 → (可选)认领 → 执行中状态更新 → 完成/取消
   │            │            │              │              │
   └────────────┴────────────┴──────────────┴──────────────┘
                              │
                         变更日志记录
```

#### 4.2.3 日报提交流程

```
填写日报 → 提交日报 → (24小时内可修改) → 查看日报
              │
         自动通知相关人
```

## 5. 非功能需求分析

### 5.1 性能需求

| 需求项 | 目标值 | 分析依据 |
|-------|-------|---------|
| 响应时间 | ≤2秒 | 用户体验要求 |
| 复杂查询响应 | ≤5秒 | 报表生成等操作 |
| 并发用户数 | ≥50 | 预估团队规模 |
| 数据量支持 | 任务数达数万条 | 业务增长预期 |

### 5.2 安全性需求

| 需求项 | 描述 | 优先级 |
|-------|------|-------|
| 认证机制 | 基于 ASP.NET Core Identity | 高 |
| 授权控制 | 基于角色的访问控制 (RBAC) | 高 |
| 数据传输 | HTTPS 加密 | 高 |
| 输入验证 | 防止 SQL注入、XSS、CSRF | 高 |

### 5.3 可用性需求

| 需求项 | 描述 |
|-------|------|
| 界面风格 | 简洁、直观、一致 |
| 错误提示 | 友好、明确、有指导性 |
| 加载反馈 | 耗时操作提供加载指示 |
| 浏览器兼容 | 桌面浏览器为主 |

### 5.4 可维护性需求

| 需求项 | 描述 |
|-------|------|
| 代码规范 | 遵循 C#/.NET 最佳实践 |
| 分层架构 | 表现层/业务层/数据层分离 |
| 依赖注入 | 提高模块独立性和可测试性 |
| 单元测试 | 核心业务逻辑需测试覆盖 |

### 5.5 可扩展性需求

| 需求项 | 描述 |
|-------|------|
| 模块化设计 | 便于添加新功能 |
| 接口化编程 | 降低模块间依赖 |
| AI服务扩展 | 便于切换AI服务提供商 |

## 6. 约束条件

### 6.1 技术约束

| 约束项 | 描述 |
|-------|------|
| 技术栈 | C#, EF Core, ASP.NET Core Razor Pages |
| 数据库 | MySQL 8 |
| .NET版本 | .NET 8 |
| AI服务 | OpenAI 兼容 API |

### 6.2 时间约束

- 开发周期有限，需分阶段交付
- 第一阶段实现核心功能（用户、项目、任务、日志）
- 第二阶段扩展功能（会议纪要、日报、AI能力）

### 6.3 资源约束

- 开发团队人数有限
- 无专职测试人员，需开发人员兼顾测试
- AI服务依赖外部API，存在网络不稳定风险

## 7. 风险分析

| 风险编号 | 风险描述 | 影响程度 | 发生概率 | 应对策略 |
|---------|---------|---------|---------|---------|
| R01 | AI服务响应不稳定 | 中 | 中 | 设置超时机制，提供降级方案 |
| R02 | 需求范围蔓延 | 高 | 中 | 严格控制需求变更，优先实现核心功能 |
| R03 | 数据库性能不足 | 中 | 低 | 优化查询，建立适当索引 |
| R04 | 用户接受度低 | 中 | 中 | 早期原型演示，收集反馈迭代 |

## 8. 假设与依赖

### 8.1 假设

- 用户具备基本的计算机操作能力
- 团队成员愿意采用新系统替代现有的分散管理方式
- AI服务 API 在需要时可用且响应时间可接受

### 8.2 依赖

- 依赖于 .NET 8 SDK 和相关 NuGet 包
- 依赖于 MySQL 8 数据库服务
- 依赖于 AI 服务提供商的 API 可用性

## 10. 需求优先级初评

基于业务价值和实现成本，对功能需求进行初步优先级排序：

### 优先级划分

| 优先级 | 定义 | 功能范围 |
|-------|------|---------|
| **P0（必须实现）** | 系统可用性的核心功能 | 用户认证、基础项目管理、任务CRUD |
| **P1（强烈推荐）** | 提升用户体验的核心功能 | 权限控制、任务指派认领、项目统计 |
| **P2（推荐）** | 完善系统功能 | 分组管理、操作日志、会议纪要、日报 |
| **P3（可选）** | 增强型功能 | AI能力、数据导入导出 |

### 分阶段交付计划（建议）

**第一阶段（P0 + P1）**：
- 用户与权限管理
- 项目管理（基础）
- 任务管理（基础）
- 分组管理

**第二阶段（P2）**：
- 权限控制增强
- 操作日志
- 会议纪要管理
- 日报管理

**第三阶段（P3）**：
- AI服务集成
- 数据统计增强
