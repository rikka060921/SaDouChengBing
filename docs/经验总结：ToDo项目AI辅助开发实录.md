# ToDo项目AI辅助开发实录

## 序言

这是一份关于在ToDo项目开发过程中如何使用AI辅助开发的经验记录。与传统文档不同，本文以"实录"形式呈现，真实记录了我们在项目中引入AI辅助开发的思考过程、实践经历以及踩过的坑。

**重要说明**：本文档描述的是"如何在开发ToDo项目时使用AI辅助"，而非"ToDo系统有哪些AI功能"。ToDo系统中确实集成了AI任务拆分、日报生成等功能，但这些是系统功能点，不是本文档的主题。

## 一、项目背景与开发痛点

### 1.1 ToDo项目简介

ToDo是一个基于`.NET 8 + Razor Pages + MySQL 8`的任务管理系统，采用分层架构设计。项目包含以下核心模块：

```
┌─────────────────────────────────────────────────────────────┐
│                      ToDo项目管理系统                         │
├─────────────────────────────────────────────────────────────┤
│  用户与权限    │ 用户管理、角色分配、权限控制                  │
│  项目管理      │ 项目CRUD、成员管理、项目统计                  │
│  任务管理      │ 任务CRUD、状态管理、认领指派                  │
│  分组管理      │ 任务分组、分类管理                           │
│  日志模块      │ 操作日志记录与查询                           │
│  会议纪要      │ 会议记录与附件管理                           │
│  日报管理      │ 日报提交与查看                              │
│  AI服务（系统功能）│ 任务拆分、日报生成等AI能力                │
└─────────────────────────────────────────────────────────────┘
```

### 1.2 开发过程中的痛点

在项目开发初期，我们遇到了以下典型问题：

| 痛点 | 描述 | 影响 |
|-----|------|-----|
| 需求描述模糊 | 业务方说"做一个任务管理"，没有具体细节 | 返工频繁，进度延误 |
| 文档撰写耗时 | 每个需求都要写详细描述、验收标准、业务规则 | 开发时间被压缩 |
| 代码重复劳动 | CRUD、数据验证、DTO转换等代码写到手酸 | 效率低，容易出错 |
| 测试覆盖不足 | 边界的件多，测试用例容易遗漏 | bug多，上线后问题多 |

### 1.3 为什么选择AI辅助

带着这些痛点，我们开始思考AI能在哪些环节帮助我们。最终，我们确定了AI辅助开发的定位：

> **AI是辅助工具，不是替代工具**
> - AI帮助处理重复性、格式化的内容
> - 人工负责决策、判断和审核
> - 人机协作，优势互补

## 二、AI辅助开发流程

### 2.1 整体流程

```
输入主题 → AI确认需求 → 需求文档 → 需求规格 → 概要设计 → 详细设计 
→ 测试计划 → 辅助开发 → 编写单元测试 → 执行单元测试 → 审查报告
```

**我们的实践模式**：
- 人工提出基础概念和核心要点
- AI进行细化和扩展
- 人工校验和纠正
- 以审核后的文档为基准进行开发

### 2.2 各阶段实践

#### 阶段一：需求确认

**人工工作**：
- 提出原始需求："需要做权限控制"
- 确定核心目标："基于角色的访问控制"

**AI辅助**：
- 分析权限控制涉及哪些实体（角色、权限、资源）
- 识别常见的权限模型（RBAC、ABAC）
- 生成初步的角色定义建议

**实际案例**：

引用全文：
```
请参考`需求：需求分析说明书`中用户与权限相关章节，帮我细化权限控制模块的需求
```

引用片段：
```
请参考`需求：需求分析说明书` 第60-100行（用户与权限相关）、第120-150行（角色定义相关），帮我细化权限控制模块的需求
```

#### 阶段二：需求文档撰写

**人工工作**：
- 提供文档框架
- 审核AI细化的内容

**AI辅助**：
- 按照文档模板细化每个需求点
- 补充标准化的字段（前置条件、输入、输出、业务规则）
- 检查文档完整性和一致性

**经验**：
- AI生成的内容必须人工逐条审核
- 特别关注业务规则和边界条件

#### 阶段三：设计阶段

**人工工作**：
- 确定技术选型
- 审核设计方案

**AI辅助**：
- 生成数据表结构建议
- 设计接口定义
- 提供代码实现示例

**实际案例**（ToDoTask实体设计）：

引用全文：
```
请参考`需求：需求规格说明书`中任务管理相关章节、`设计：概要设计说明书`中数据模型设计，帮我完成ToDoTask实体的详细设计
```

引用片段：
```
请参考`需求：需求规格说明书` 第180-250行（FR-TASK相关）、`设计：概要设计说明书` 第80-120行（数据模型设计），帮我完成ToDoTask实体的详细设计
```

#### 阶段四：代码开发

**人工工作**：
- 审核AI生成的代码
- 处理复杂业务逻辑

**AI辅助**：
- 生成基础CRUD代码
- 生成DTO转换代码
- 生成验证逻辑

**实际案例**：

引用全文：
```
请帮我完成ProjectDomainService的开发，参考文档：
- `设计：详细设计说明书`
- `设计：概要设计说明书`
- `需求：需求规格说明书`
```

引用片段：
```
请帮我完成ProjectDomainService的开发，参考文档：
- `设计：详细设计说明书` 第150-200行（ProjectDomainService相关章节）
- `ToDoTaskDomainService.cs`（参考现有DomainService实现模式）
```

#### 阶段五：单元测试

**人工工作**：
- 确定测试范围
- 审核测试用例

**AI辅助**：
- 生成测试方法框架
- 生成测试数据构造代码
- 补充边界条件测试

**经验**：
- AI生成的测试用例需要人工补充断言逻辑
- 特别注意边界条件和异常情况

## 四、踩过的坑

### 4.1 Prompt理解偏差

**问题描述**：
AI理解的需求与实际意图不符，导致文档返工。

**教训**：
- Prompt中的"可以"和"必须"要明确区分
- 重要约束要在Prompt中重复强调
- AI输出必须逐条人工审核
- 引用文档时要明确指出关键章节

### 4.2 过度依赖AI

**问题描述**：
团队成员过度信任AI输出，缺少人工审核。

**案例**：
AI生成了一段数据验证代码，团队成员直接使用。后来发现AI漏掉了一个边界条件检查，导致线上bug。

**教训**：
- AI输出必须人工审核后才能使用
- 关键逻辑（权限、金额计算等）要格外谨慎
- 建立代码审查机制
- 引用文档时人工确认AI是否正确理解了上下文

### 4.3 Prompt信息不足

**问题描述**：
Prompt中缺少关键信息，导致AI输出不准确。

**教训**：
- Prompt要尽量完整，补充必要的上下文
- 重要约束要明确列出
- 必要时提供示例
- 引用相关设计文档时明确章节范围

### 4.4 输出格式不稳定

**问题描述**：
相同Prompt多次调用，输出格式不完全一致。

**案例**：
让AI生成3次需求文档，输出的章节结构和格式各不相同。

**教训**：
- 明确指定输出格式和结构
- 提供模板或示例
- 使用temperature参数控制随机性（设为0.3）
- 引用已有文档时明确指定章节，确保AI理解上下文

## 五、经验总结

### 5.1 有效做法

| 做法 | 说明 | 效果 |
|-----|------|-----|
| 角色定义 | 让AI扮演特定角色（如"资深架构师"） | 输出质量明显提升 |
| 分步提问 | 先问大问题，再逐步细化 | 避免信息过载 |
| 示例引导 | 提供输入输出示例 | 格式更稳定 |
| 约束明确 | 明确输出限制（字数、格式、条数） | 减少返工 |
| 迭代优化 | 先让AI生成，人工反馈后修正 | 效率和质量平衡 |

### 5.2 无效做法

| 做法 | 问题 | 后果 |
|-----|------|-----|
| 一次问太多 | AI输出信息过载 | 重点不突出 |
| 模糊提问 | "帮我看看这个代码" | 输出泛泛而谈 |
| 完全放手 | 不审核AI输出 | 错误流入下游 |
| 过度质疑 | 反复让AI重写 | 效率反而降低 |


## 六、效果评估

### 6.1 效率提升

| 阶段 | 传统方式 | AI辅助后 | 提升幅度 |
|-----|---------|---------|---------|
| 需求分析 | 2-3天 | 0.5-1天 | 60-70% |
| 文档撰写 | 1-2天 | 0.5天 | 50-60% |
| 代码开发 | - | - | 30-40% |
| 单元测试 | - | - | 40-50% |

### 6.2 质量改善

| 指标 | 传统方式 | AI辅助后 |
|-----|---------|---------|
| 需求遗漏 | 较多 | 明显减少 |
| 边界条件覆盖 | 不足 | 有改善 |
| 文档规范性 | 不一致 | 格式统一 |
| 代码规范遵循 | 参差不齐 | 有提升 |

### 6.3 局限与不足

1. **业务理解局限**：AI对复杂业务逻辑的理解仍有偏差
2. **创意能力不足**：无法生成突破性的设计方案
3. **上下文保持**：长对话中后文可能遗忘前文
4. **安全敏感**：涉及敏感信息时需要谨慎使用

## 结语

AI辅助开发是一个"人工主导、AI辅助"的过程。在ToDo项目中，我们深刻体会到AI在提升效率、减少重复工作方面的价值。但同时也认识到：

> AI是强大的工具，但不是万能的工具。善用AI，审慎对待其输出，才能真正发挥人机协作的优势。

希望这份"实录"能为其他团队在引入AI辅助开发时提供一些参考和借鉴。
