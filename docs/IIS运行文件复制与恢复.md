# IIS 运行文件复制与恢复

应用健康检查成功不代表附件和项目资料一定可用。数据库记录仍存在但下载返回 404 时，需要核对当前发布目录中的实际文件。

旧部署脚本将整个 `App_Data` 或 `uploads` 目录复制到已存在的目标目录，可能生成 `App_Data/App_Data` 或 `uploads/uploads`。新脚本按文件的相对路径复制内容，先停止应用池中的写入者，再复制并校验文件，最后切换发布目录。复制失败会沿用已有回滚流程，不将不完整目录作为新站点。

运行文件复制保留源文件，对每个目标进行路径和 SHA256 检查，拒绝目录联接或符号链接，避免复制到预期目录之外。目标中的发布默认文件按原有策略由实际运行文件取代；复制源目录本身不会多套一层子目录。

## 已部署站点的恢复

恢复脚本读取 IIS 当前站点的物理路径，并限制在指定站点根目录的 `releases` 下。它检查嵌套的运行目录，把缺失文件复制回应用预期的位置，不删除原目录，不覆盖不同内容的现有文件，不改数据库，不生成资料新版本，也不重启应用池。

服务器先更新代码，再运行恢复脚本。例如当前站点为 ToDo2：

```powershell
git -C 'C:\Deploy\ToDo-source' pull --ff-only origin 'Work-miracles(SaDouChengBing)'
& 'C:\Deploy\ToDo-source\deploy\Repair-ToDoIisRuntimeFiles.ps1' -SiteName 'ToDo2' -SiteRoot 'C:\inetpub\ToDo2'
```

加 `-WhatIf` 可先看恢复范围而不写文件。结果中的 `Copied` 是本次恢复文件数，`Identical` 是已存在且内容一致的文件数，`PreservedDifferent` 是保留的不同内容文件数。若存在不同内容，应分别核对两个版本，不盲目覆盖。重复运行会跳过已经恢复的相同文件。

若检查结果没有发现嵌套目录而资料仍无法下载，应继续检查存储路径、目录权限和文件是否仍保存在旧发布目录；不能把健康检查当作资料恢复证明。

### 深层嵌套与长路径

恢复时每一层的内容直接复制到标准运行目录，不再将下一层同名目录整体复制出来。原来的所有嵌套目录仍保留，恢复不会生成更多中间副本。最多检查 64 层；超过限制会明确报错，不删除数据。

运行文件模块通过同目录的 `ToDoRuntimeNative.cs` 使用 Windows 长路径文件接口，在 Windows PowerShell 5.1 和 PowerShell 7 下支持超过 260 字符的源、目标路径。无需修改系统长路径注册表。临时文件使用短的独立名称，SHA256 校验后在同目录发布；失败时只清理本次唯一临时文件。

恢复发布文件时使用原子“不覆盖”操作，即便运行中的应用同时上传了同名文件，也保留该文件，报告冲突而不是用历史版本替换它。

必须一起更新上述 C# 辅助文件和 PowerShell 脚本，不要只复制单个脚本。若旧版恢复中途失败，已恢复的相同文件会跳过；更新后重跑即可继续，不需要重新导入项目资料。

## 脚本版本

修改部署脚本后，先执行 Git 更新，再调用脚本。脚本执行过程中虽然会拉代码，但已经加载的 PowerShell 脚本和函数不会因此自动变成新版本。

## 本地验证

```powershell
& '.\deploy\Test-ToDoIisRuntimeFiles.ps1'
```

测试使用独立的忽略目录，不接触 IIS 或业务数据库。覆盖已存在的发布目录、子目录冲突、重复复制、多层恢复、保留现有内容、WhatIf、路径重叠、文件目录冲突及目录联接拒绝。额外覆盖 9 层同名目录恢复、不生成中间副本、超过 500 字符的源和目标路径、中文长文件名、长路径覆盖与校验，以及源/目标和排除分支中的目录联接拒绝。
