## 日常交付

1. 在原目录修改，检查 diff，完成必要功能验收，检查密钥及私有内容。
2. 显式添加本轮文件，编写详细提交说明（修改内容、原因、验证结果），提交到本地团队分支。
3. 用 PowerShell 7 在原目录运行：

```powershell
.\deploy\Sync-ToDoRepositories.ps1
```

如果当前终端是 Windows PowerShell 5.1，先打开 PowerShell 7；本机已安装的运行时也可以这样调用：

```powershell
& 'C:\Users\Administrator\.cache\codex-runtimes\codex-primary-runtime\dependencies\native\powershell\pwsh.exe' -NoProfile -File .\deploy\Sync-ToDoRepositories.ps1
```

本机网络需要代理时追加 `-Proxy 'http://127.0.0.1:7890'`，不修改全局 Git 代理。
只检查仓库状态、远端和待发布快照时追加 `-CheckOnly`：会 fetch 并创建本地临时对象，不编译、不提交、不推送。

默认流程：检查干净工作区与分支 → fetch 校验两个远端 → 生成排除运行数据的候选树 → Release 测试 → Release/Debug 编译 → 创建独立 GitHub 快照提交 → 推送团队 → 推送 GitHub → 分别核对远端提交。
`-SkipValidation` 仅供已经验证同一 HEAD 的重试和隔离脚本测试，日常不要使用。
配置文件变更默认阻止公开发布；确认没有密码/密钥后才可使用 `-ApproveConfigurationChanges`。这不替代人工安全审查。

后续本对话及遵循根目录 AGENTS.md 的开发代理，会在完成开发验证后执行这个流程。
**没有安装定时任务、保存监听或 post-commit 自动推送钩子。** 自己在 Visual Studio 提交并不会自动双推；手动开发时仍需运行上述脚本。这样避免半成品、误提交或正在排查的代码立即公开。

新电脑先准备原目录和公共镜像、确认两边快照关系并设置此本地配置；不要把内部历史作为 main 推向 GitHub。

## 失败与重试

两个远端无法事务性推送。输出 `TEAM VERIFIED` 后出现网络错误，意味着团队可能已成功而 GitHub 未完成。
保留源 HEAD 及公共镜像中的准备提交不变，再运行同一命令。脚本支持准确匹配原任务的重试。
若准备期间又提交新修改，先完成旧版本同步或审查恢复，不强推、不删除镜像中的提交。
成功会同时输出 `TEAM VERIFIED`、`GITHUB VERIFIED`。成功推送不等于服务器已部署。
