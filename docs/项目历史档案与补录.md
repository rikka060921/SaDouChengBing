# 项目历史档案

历史资料补录不应把已过期的任务重新投入执行，也不应根据聊天补造会议原话或验收记录。

## 用户入口

- 项目导航中的“历史档案”。
- 项目任务页面中的“历史任务”。
- 按项目筛选的会议纪要页面中的“历史会议”。
- 原始文件仍在“项目资料”中，可按分类查找和下载。

历史档案为只读内容快照，保留原状态、原责任人、日期口径与来源。原记录仍保留在原项目。原链接继续受原项目权限限制；快照受目标项目权限保护。

档案不会创建业务任务或会议，不触发 Agent 派单、行动项提取、催办、审核或日报补造，也不影响当前项目任务完成率。需要继续的工作应另建正式任务并注明档案来源。

## 存储和维护

使用现有项目资料版本机制保存 `project-history-archive.json`，无需新增数据库字段或迁移。页面只读取目标项目中该文件的当前版本，不读取任何其他项目的档案文件。

档案格式版本为 1，文件包含目标 `ProjectId`、实际快照时间 `RecordedAt` 和 `Records`。每条记录包含：

- `Key`：稳定、唯一的来源编号，避免重复记录。
- `Kind`：`task` 或 `meeting`。
- `Title`、`DateLabel`、`Owner`、`Status`：原记录信息；未知字段留空，不推测。
- `SourceLabel`：来源项目、记录编号或原始文件，以及必要的真实性说明。
- `SourceUrl`：可空；有值时只允许本站对应任务或会议的详情路径。
- `Body`：可核查的原内容及必要的来源说明。
- `ContentHash`：正文 UTF-8 字节的 SHA256，用于检测整理或传输过程中的不一致，并非对来源真实性的认证。

管理员在项目资料上传经过核查的档案文件。只追加新版本，旧版本按资料机制保留；重复补录时应先比较文件内容哈希，不为同一快照重复上传。

页面验证格式版本、所属项目、唯一编号、字段长度、正文哈希和来源链接，最多 500 条、单文件 8 MB。校验失败会显示错误，不影响现有任务和会议。正文作为纯文本编码展示，不执行其中的脚本或指令。

## 来源边界

Git 提交说明、AI 总结、用户笔记、系统原有会议与逐字转写属于不同来源。应分别标注，不能将 AI 总结或笔记标为真实逐字原话。只有文件名日期的材料必须明确标为文件日期；没有会议日期或发言人身份时保持缺失。

原始会议、任务、附件及业务资料都属于运行数据，不随此功能提交到公开源码仓库。
