# Agent 执行与验收可靠性优化

日期：2026-09-22。基于本地 `dcea4c4`，本轮仅修改和测试，不提交、不推送、不部署。

## 优化原则

保持三个业务字段创建 Agent、普通任务自动推进的既有流程。本轮不增加评分、配置项或人工审批步骤，优先处理实际造成空转、卡住、错误完成的问题。

## 改了什么，为什么改

### 1. 普通回答不再无谓续跑

手动启动的 Agent 把系统记录的 `context.read` 也当作需要下一轮处理的工具结果。即使已经给出完整回答，只要读取了项目资料，仍可能继续请求模型，直到达到轮数上限。

现在与任务自动执行队列保持一致：上下文读取只是审计记录，不单独触发续跑；真正调用业务工具后仍继续处理工具结果。减少无效等待和重复模型请求，不减少资料读取或权限审计。

### 2. 服务停止后恢复原尝试，不因次数边界卡住

原来服务停止会把运行中的工作标记为“等待重试”，但达到尝试次数上限的工作又不能被领取，可能永久停留在该状态。

现在正常停机中断后回到可继续处理的队列状态，保留原尝试次数、会话和已执行工具记录。服务恢复后继续；如果随后真的执行失败，仍按原次数上限终止，不无限重试。

两类队列均增加测试：先实际保存一条评论，再模拟停机并恢复，确认没有重复评论、没有新建第二个会话。此修复针对应用捕获到的停机取消；不等于覆盖所有断电、外部系统写入中断场景。

最终复核还发现首轮执行在整轮返回后才关联会话：工具已保存、整轮返回前停机时，恢复可能创建新会话。现在在任何模型和工具调用前保存工作项与会话关联；启动事件失败时清理会话运行状态，工具处理期间的停机取消不再把已成功操作改写成失败。

补充用例分别在会话启动事件、评论实际落库后的工具事件中断；恢复时让模型重放相同工具调用标识，验证沿用原会话、保留成功记录且只存一条评论。这不是对模型换一个调用标识重做同一动作、或所有外部写入的通用“恰好执行一次”保证。

如果取消时工具仍处于未确认执行结果的状态，则明确保存为失败并提示核对；不把未知结果当成功、不删除审计，也不盲目重执行可能有副作用的操作。新增业务写入前中断测试验证：没有写入评论，重放相同调用仍保留失败记录，自动验收在服务端检查阶段即拒绝通过。

本轮没有读取或修补业务数据库中可能已经卡住的历史记录；不能把代码修复当成旧任务已被恢复。

### 3. 失效任务不阻塞其他任务的后台派单

以前后台按时间取前十个待调度任务，一个失效发起人可能中断这一轮补偿；反复查询同一批任务又会阻塞后面的正常任务。

现在在截取批次之前过滤当前无权派单的任务，并隔离查询后发生撤权、任务状态变化等预期异常。不擅自替换为管理员身份，不自动通过已有的人工确认决策。

### 4. 派单权限以当前身份和项目为准

原来“任务创建者”身份可以单独满足派单检查，没有要求创建者仍属于项目。

现在入口和后台补偿共用权限筛选：账号须正常、项目未删除；系统管理员、项目负责人、项目管理员，或仍在项目中的任务创建者才能派单。确认候选时同样复核权限。已有管理员和正常成员的合法操作保留。

### 5. 自动验收不沿用复核前已经失效的资料

模型复核需要时间，期间可能新增子任务或补充工作项，也可能有人删除、改写待验报告。以前只重新读取 Agent 配置的通用资料：如果没配置相关数据源，或者修改发生在报告前 800 字摘要之后，就可能漏检。

现在复核后重新检查未完成子任务和其他待处理工作；对本次真实创建的报告重新读取完整正文及关键归属字段。发生变化时保留交付，说明需要重新核对的原因，不凭旧资料自动完成，也不因此重跑已经完成的业务写入。
